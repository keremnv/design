# Minimum usable Design product audit

**Status:** product / architecture audit, 2026-09-27. **Not a contract, accepted architecture, implementation plan, or roadmap authority.** This is an independent reading of the current tree, including uncommitted application work. Executable paths and tests take precedence over the cited architecture notes. No production code was changed for this audit.

## 1. Executive conclusion

**Design is a bounded software-governance application that publishes an inspectable, historically retained interpretation of dispersed requirements and software evidence, then judges named software subjects against that exact interpretation.** The smallest usable product is one declared config-route profile, a fresh-publication command, discovery and evidence reads, a profile-specific judgment command, a useful UNKNOWN follow-up, and a conservative W0/W1 read. It is not an autonomous workspace interpreter. The required input is at least a supported source pair **and** a declared rule for interpreting it; `here is my workspace` alone is insufficient.

Core already supplies most epistemic storage and read primitives. Design has production construction, read, case, judgment-artifact, and investigation helpers, and 47 focused acceptance tests pass. The **product loop is absent**: the config script is fixed to repository fixtures; callers must know proposition and subject identities and invoke separate Python functions; interpretation rules are implicit in fixture constants; there is no supported Design comparison or guarded continuation from a proposal to a new construction. The largest blocker is therefore the **declared, workspace-parameterized profile and thin product front door**, with semantic-establishment discipline inside it. A CLI alone around the current hard-coded fixture would not solve that blocker.

The proposed graph criterion survives with a narrower wording: preserve the **epistemic consequence actually relied upon**, in a sealed World or reconstructible retained evidence and exact external artifact references. Preserve a decision's changed standing if it affects later governance. Ordinary exploration, failed proposals, and tool attempts need not become World relations. No generic Action, Admission, Decision, or application runtime is forced by the bounded read.

## 2. First-principles product model

The user needs to (a) select a bounded evidence universe and interpretation profile, (b) publish the current understanding, (c) find claims and their basis, (d) ask a question about a named subject, and (e) correct evidence or a rule and publish again. These are user transitions, independent of package names. “The World is how the specification is currently understood” is useful only **relative to declared scope, source revisions, and construction method**. The World does not become the specification, and “current” cannot mean live-source aligned without another observation. An exact World may remain historically true about R0 while the workspace has advanced to R1 ([Core baseline](CORE_PRODUCT_V1_BASELINE.md), [intake probe](SOFTWARE_GOVERNANCE_CONSTRUCTION_INTAKE_INTEGRITY_EXPERIMENT.md)).

The four verbs are sufficient as a navigation model, but not four equally mandatory subsystems. **Construct, Inspect, and Judge** are the minimum daily loop; **Investigate** is a bounded continuation when an UNKNOWN has a discoverable basis. Its currently tested case expansion is mostly a repair of an intentionally omitted case fact; default case assembly already includes the producer facts. The useful second path is inspecting retained manifestation/source material and proposing a missing fact or interpretation. Repeated **Construct** is revision; a separate revision engine is not earned. Publication and conservative comparison are needed product operations, not new semantic stages.

## 3. Product invariants

Five principles suffice for this slice:

1. **Publish bounded interpretations at fresh, sealed, exact addresses; retain prior addresses and evidence.** A mutable “latest” pointer is convenience only.
2. **Every operative semantic assertion has an inspectable source/producer basis and a declared profile rule.** Mechanical admission checks structure and recorded support; it cannot certify truth or exhaustive dependencies.
3. **Represent consequential uncertainty and coverage explicitly.** Absence licenses a negative only under a relevant, justified completeness claim. A claim of `COMPLETE` is itself a fallible profile assertion, not proof of the external universe.
4. **Judge only against one verified publication and a named profile method.** Applicability, software finding, and conformance are separate, and unsupported conclusions remain UNKNOWN.
5. **Retain the consequence relied upon across sessions.** Process state can expire, but the published assertion, its evidence, an adopted correction/exception, and any judgment artifact later cited must remain recoverable by exact reference.

These subsume the ten suggested principles. Falsification pressure: the current constructor does not yet satisfy 1 fully; fixture bindings do not satisfy 2 adequately; the judgment case verifier only partly satisfies 4. Principles 2 and 5 do **not** demand a generic admission layer or that every receipt be inserted into the graph.

## 4. Construct audit

The config route producer takes a JSON path, reads it once, creates `config_member`/`config_route` mechanical assertions, snapshot-local subjects and retained bytes ([producer](../profiles/software_governance_config_v0/produce.py)). The profile build script combines that output with Markdown observations and hand-authored `PropositionSpec`, `BindingSpec`, candidates, questions and `CompletenessSpec`; the generic constructor copies the producer World, asserts Design relations, writes blobs/sidecars, validates, and publishes ([build](../profiles/software_governance_config_v0/build.py), [constructor](../ontology_author/software_governance/construction.py), [validator](../ontology_author/software_governance/validation.py)). It returns the output path. This is a real production path for the **fixed fixture**. The installed `author` CLI does not expose it, and `ontology_author.software_governance.__main__` exits with fixture usage text. `profiles/` is excluded from the installed package ([packaging](../pyproject.toml)).

Cold start from “my workspace”: the caller must discover supported source type (**profile configuration**); identify the route JSON and governance Markdown (**legitimate product input** once selected); identify authoritative paragraphs (**profile rule**); know route IDs and correspondence rule (**currently hidden fixture knowledge**); name proposition IDs, coverage universe and gaps (**profile rule/output**); select a fresh retained address (**product surface**); optionally supply an expected source revision from an earlier observation (**legitimate precondition**). The script accepts only the address, uses `PROFILE_ROOT` and exact English sentences, and has no workspace/source parameters. General arbitrary workspace discovery is an **acceptable limitation** of a bounded product; presenting the fixture as general workspace construction would be a false claim.

The config producer supports a narrow textual JSON form: `_object_span` searches for the literal pretty-printed `"id": "…"`; compact valid JSON may fail. It does not reject duplicate route IDs. These are profile correctness gaps when the slice claims a complete route enumeration or cross-publication matching, not reasons for a universal adapter ([correspondence probe](CONFIG_ROUTE_CORRESPONDENCE_CONTRACT_EXPERIMENT.md)).

## 5. Inspect audit

Core can discover schema, paginated rows, referents, assertion warrants, derivations and completeness; its bundled inspector and `/world/*` endpoints are generic ([explorer](../ontology_author/world/explorer.py), [server](../ontology_author/world/server.py)). Design's `GovernanceView` answers proposition↔subject, proposition/binding basis, candidates/questions, manifestations, mechanical facts and governance coverage ([reads](../ontology_author/software_governance/reads.py)). An informed Python caller can list `software_subject` and `governance_proposition` via `relation_rows`, but the Design view has no explicit inventory or publication comparison method. Assertion support is reachable through Core and case facts. The current `inspect_governance_binding` returns a construction-method string, `relation_support`, endpoint-resolution label and governance-source observation; it does not itself reconstruct the software-side evidence named by the free-text `software_evidence` field. A consumer can inspect the subject separately, but that does not explain **why this proposition was matched to that subject**.

W0 is readable by its retained path. W1 is readable by another path. No supported Design W0→W1 read explains added/removed/changed propositions, bindings, evidence, unresolvedness, or coverage. A raw tuple diff is unsafe for software subjects because the config producer embeds the whole-document digest in subject IDs. Current `record_id` is observed but has no unique, persistent, never-reused identity contract. The first slice can compare exact proposition IDs and separately show each World's subject rows, route properties and grounding; it must label any same-record-ID association **candidate/observational** and must not infer binding renewal ([correspondence probe](CONFIG_ROUTE_CORRESPONDENCE_CONTRACT_EXPERIMENT.md)).

## 6. Judge audit

The caller can assemble a bounded case, verify each cited assertion and reconstructed support, call `profiles.software_governance_config_v0.judge.judge`, and use `consumer_reads` to inspect the resulting JSON ([case](../ontology_author/software_governance/judgment/case.py), [artifact](../ontology_author/software_governance/judgment/artifact.py), [config evaluator](../profiles/software_governance_config_v0/judge.py)). Tests establish `APPLIES`, `DOES_NOT_APPLY`, and `UNKNOWN`; `CONFORMS`, `CONFLICTS`, and `UNKNOWN` only after applicability; source-backed assertion IDs and rule parameters ([tests](../tests/test_software_governance_judgment.py)). Missing binding under incomplete coverage remains UNKNOWN. An explicit handler mismatch permits `DOES_NOT_APPLY`. A binding is evidence for applicability; it is not that verdict. The evaluator's `RULE` is hard-coded independently of the governance paragraph, so a corrected requirement can leave Judgment applying the old `/customers/export` rule unless the profile changes too.

No one production call accepts just World address, proposition and software subject. The caller must choose the correct evaluator, invent a question/case ID, verify the case, invoke the evaluator, decide where to write artifacts, and join case+artifact for reads. The evaluator is profile code, not a registered installed command. `verify_case` compares World ID and individual citations but **does not compare `world_address` or revision to the opened publication**, check selected IDs/omitted facts, or verify an evaluator artifact. The artifact does not carry the exact publication address; `consumer_reads` obtains it from the accompanying case. Thus “verified Judgment artifact” is too strong for the current raw composition: its cited input facts can be verified, while the conclusion and address association require the trusted profile caller. The smallest facade should enforce the exact address, method/profile match, result shape and cited assertion references, retain case plus artifact together when the answer will be reused, and say clearly that verification is of recorded basis, not semantic truth.

## 7. Investigate audit

The generic package can create questions/receipts/proposals and expand a case with verified facts from the **same** publication ([investigation package](../ontology_author/software_governance/investigation/)). The config investigator can inspect all producer facts, add already-published assertions omitted from the initial case, or reconstruct an unasserted route field from a manifestation and return a proposal. Exploration lineage is on the receipt; only facts actually cited by a later evaluator support that Judgment. The tests demonstrate missing `path` → expanded case → `CONFORMS`, an unasserted `approval` field → proposal, and an unresolved construction gap that stays unresolved ([tests](../tests/test_software_governance_investigation.py)).

There is no generic investigator planner, nor is one needed. A normal default case already includes the route fact, so the case-expansion success is an edge case rather than the usual user journey. A proposal is currently a production dead end: there is no intake that turns it into a producer assertion or a new semantic construction rule. This **does not block** a first slice if UNKNOWN can show its type, relevant evidence, and a concrete correction path. It **does block** any claim that Investigation automatically resolves UNKNOWN or publishes discoveries. Construction ambiguity requires new evidence or a revised interpretation, not more citations from W0.

## 8. Revision/reconstruction audit

The constructor refuses a pre-existing output in ordinary cases and can create W1 at a second address while W0 remains untouched. Source bytes or supplied semantic specs may differ. The test-local write/operational probes show same software bytes with different governance Worlds and a source change with no automatically carried binding ([write probe](SOFTWARE_GOVERNANCE_WRITE_SEMANTICS_EXPERIMENT.md), [loop probe](SOFTWARE_GOVERNANCE_END_TO_END_OPERATIONAL_LOOP_EXPERIMENT.md)). Those probes are not a production continuation mechanism. Today `build_config_profile` always supplies the same fixture correspondence and reads its own paths, so a user cannot feed a corrected interpretation without editing profile code or manually reproducing test orchestration. Reconstruct is repeated construction against selected revised inputs, with an explicit rule re-evaluation; no separate “Revision” semantic object is needed. Legacy `author rebuild` overwrites and is unsuitable for this history ([Core baseline](CORE_PRODUCT_V1_BASELINE.md)).

## 9. Specification → World loss

The main risk is **silent selection of the wrong meaning**, not a missing Core relation. The route profile chooses exact paragraphs, derives proposition IDs from constants, selects the `customer-export` route by a known ID, labels the support `SOURCE_EXPLICIT` and endpoint `DETERMINISTIC`, and passes only the paragraph observation into the binding. Neither the validator nor the World proves that this paragraph establishes this route correspondence. The validator checks a recoverable source observation, nonempty method/support labels and a subject receipt, not the truth or sufficiency of the mapping ([build](../profiles/software_governance_config_v0/build.py), [validation](../ontology_author/software_governance/validation.py)). The software-side basis is currently a string (`"json route record"`), so a future consumer may reconstruct both endpoints separately but not the actual matching rule.

Other losses: unsupported/ignored source formats, the producer's fragile span locator, duplicate IDs, missing evidence adapters, unmodeled source files, stale profile code, and session/human decisions never recorded. The product exposes retained evidence, constructed rows, method labels, candidates and a deliberately `INCOMPLETE` binding coverage claim. It does **not** expose a source inventory showing what was scanned versus skipped, an inspectable versioned semantic establishment rule, or a reliable correspondence-basis link. The minimum correction interface needs explicit profile input scope, a construction result listing selected/skipped/unsupported inputs and coverage, and a rule/basis identifier recoverable with each semantic assertion. No universal discovery or admission subsystem follows.

## 10. World → software loss

The judgment model usefully separates applicability, software finding and conformance. `UNKNOWN` plus construction/judgment gap labels prevents an absent binding or missing fact from becoming `CONFLICTS`. The config evaluator can still conflate a bad World and bad software if its hard-coded rule is wrong or a binding is incorrectly established. A `CONFLICTS` verdict means **software differs from the evaluator's recorded rule, under this World's commitments**; it does not prove the source specification or constructed correspondence was correct. The product must display the proposition source, binding basis, evaluator rule and exact publication beside a conflict. A missing/uncertain binding must not be treated as implementation blame. If a newly discovered source field is not asserted in W0, Investigation may propose it; judgment of W0 must remain unchanged until a new World exists.

## 11. Wrong-specification correction path

If the implementation matches the stated requirement but that requirement was wrong, correct the authoritative Markdown/source evidence (or supply a separately authoritative correction), retain its old bytes, run the same declared profile on the new source revision, and publish W1 at a fresh address. W0 and its old Judgment remain valid accounts of the old interpretation. W1 needs its own proposition/binding and evaluator rule, with version or fingerprint changed when the rule changes. The profile must reject a source change it cannot translate into its evaluator rule; otherwise W1 could contain new wording while the evaluator silently uses the old threshold. Compare W0 and W1's proposition wording, grounding, correspondence, rule basis and resulting judgments. Current Core and Design primitives can represent these states. The missing piece is a workspace-capable profile that recognizes corrected text instead of exact fixture sentence constants, plus the comparison/read surface. If a human override is operative without changed source, it must become retained evidence or an explicit profile-grounded semantic assertion in W1; a chat transcript silently consulted by the evaluator is insufficient.

## 12. Durable graph / ephemeral process boundary

The boundary is reliance, not artifact type. A fact may stay in an external retained artifact if a later answer can recover it by exact reference; the graph need not contain every process object.

| Artifact | Why outside the World now | When its consequence must survive | Existing representation? |
| --- | --- | --- | --- |
| Case | Bounded presentation of selected W assertions | When a later judgment relies on that exact selection | Retain case with artifact; assertions remain in W |
| Judgment | Derived conclusion about one W under a profile method | When cited for audit or later decision | Retained JSON + exact W/method/case; do not rewrite W |
| Investigation receipt | Exploration lineage, not support | When discovery/proposal or expanded case is relied on | Retained sidecar; assertion IDs and W address |
| Proposal | Unaccepted possible fact/interpretation | When adopted into later knowledge or needed to explain correction | W1 assertion + grounding; proposal may remain evidence |
| Operation bridge | Event-scoped cross-publication navigation, not identity | When historical operation-to-current-subject correspondence is relied on | Retained exact-address sidecar; ordinary relation if established and reusable; no generic bridge required |
| Action outcome | Attempt/result is not observed source truth | When outcome drives later governance or a dispute | Retained bounded outcome plus independent observation; W assertion only if the event itself becomes governed knowledge |
| Manual decision | Standing is application-specific | When it changes which interpretation/exception is operative | Retained decision evidence plus W1 grounded commitment, if within judged scope |
| Correspondence sidecar | Cross-snapshot comparison may be conditional | When used to select affected historical context | Retain basis/method and exact W0/W1; never silently renew binding |

The test-local operational and correspondence work supports this conditional boundary. No production artifact registry or lifetime policy currently ensures retention of cases, judgments, receipts or sidecars. If Agent B must rely on them, the product must store the exact referenced files or intentionally reconstruct the answer from a World. An abandoned scratch proposal need not be retained. “Processes may disappear; durable epistemic consequences may not” is a useful product rule **only with this reliance condition**.

## 13. Semantic establishment audit

`governance_binding(P,S)` means an **established concern/correspondence** between proposition P and a mechanically identified SoftwareSubject S, grounded by its correspondence basis. Construction marks it `SEMANTIC`; the generic validator rejects ambiguous/unresolved endpoint labels and candidate/binding duplication; `GovernanceView` navigates on bindings; Judgment requires a binding **plus profile rule and subject kind** for `APPLIES` ([construction contract §7](SOFTWARE_GOVERNANCE_CONSTRUCTION_CONTRACT.md), [constructor](../ontology_author/software_governance/construction.py), [validator](../ontology_author/software_governance/validation.py), [evaluator](../profiles/software_governance_config_v0/judge.py)). It does **not** mean organizationally adopted, in force, mandatory, or APPLIES. A binding may coexist with mechanically unresolved target information in the mail profile; it concerns the occurrence, not a chosen target.

The ambiguity is in **establishment**, not storage: `BindingSpec` supplies a row, and `support`, `endpoint_resolution`, `construction_method`, `software_evidence` are caller-provided strings. Validation ensures they are present and non-ambiguous, not that the supplied evidence licenses the correspondence. The profile's `by_id["customer-export"]` plus English paragraph is an implicit rule, but no profile contract states how names, route IDs, evidence spans and endpoint choice entitle emission, what other evidence was considered, or when to emit a candidate instead. The current versioned profile ID and method text make the origin inspectable at a coarse level, not reproducible as a rule. This is a **minimum-product blocker for generalizing the config fixture into a usable bounded profile**, not a Core architecture gap. The smallest remedy is a declared, versioned profile-specific proposition extraction and binding rule (including ambiguity/unsupported cases), source and software observations on the binding or inspectable references to both, and a validation/control case that refuses unsupported correspondence. `SOURCE_EXPLICIT` should be used only if the source actually identifies the endpoint under that declared rule. No generic Admission subsystem is warranted.

| Concept | Product question and durable fact | If removed / current limit |

| `governance_known_gap` | “Which omission limits coverage?” Named inspectable gap | Specific failure reason lost; could be folded into a structured completeness record, but current separate row is cheap and useful |

The optional `proposition_semantic_subject` read, Program Spine convenience reads, and historical Core obligation/resolution tables are not needed for the config slice. `domain_relation` is a human/profile label in the proposition row, not an executable predicate; its product necessity is weaker than the proposition's identity and text. `software_manifestation` is useful for the demonstrated proposal path but remains optional. No new graph noun is forced.

## 14. Agent usability

Agent B can reopen W0 by exact address and inspect its assertions, source text, origin and unresolved question without Agent A's transcript. B cannot safely continue the full loop from W0 alone: profile selection, establishment rule, omitted input inventory, judgment case/artifact pairing, artifact retention and W0/W1 comparison are external or implicit. A sealed World is also not automatically aligned with the live workspace. An agent harness would be downstream leverage once those small surfaces exist; it should not own governance truth or add Core machinery.

## 15. Production surface audit

The installed `author` command serves Core workspace creation, replacement rebuild, list and inspector; it is not a Design command. `governance` is a separate historical application CLI ([packaging](../pyproject.toml), [Core CLI](../ontology_author/world/cli.py)). The Design `__main__` wrapper only prints a fixture usage message. The generic inspector can view relations and warrants at a selected World, but does not assemble a Design question. A **thin Design CLI or Python facade with structured JSON** is enough: `construct` with source/profile/output, `list/inspect` for publications under a declared output root and one exact address, `judge` with proposition/subject, `investigate` for an UNKNOWN, and `compare` for two exact addresses. These may be one CLI with Python functions beneath it; there is no need for a frontend rewrite, selector database, agent API server or workflow object. A profile must be explicitly selected or discovered from a small bounded config, not inferred from arbitrary repository prose. Listing addresses is discovery; designating one “current” requires an explicit policy or fresh source-alignment check.

## 17. Research debt / consolidation state

**Established understanding:** sealed fresh-address Core history; source/knowledge/action separation; binding as concern; candidate versus established; absence under coverage; case facts versus applicability; same-publication investigation; snapshot-local subjects. **Production mechanism missing:** guarded expected-revision intake, stronger config inventory checks, explicit establishment rule, safe publication order, conservative comparison and artifact pairing. **Product exposure missing:** workspace-parameterized construction, discovery, one-call judgment and UNKNOWN continuation. **Research only:** conditional route-key persistence, operation bridges, execution outcomes, reconsideration and operational loop helpers. **Obsolete/superseded for this slice:** old graph/MCP entrypoints, checkout-specific GovernanceCase and authority/semantic-binding machinery as mandatory stages ([research inventory](research/README.md), [Core baseline](CORE_PRODUCT_V1_BASELINE.md)).

More research on a generic workflow or taxonomy would now increase debt. The next useful evidence is a production bounded slice with real non-fixture config inputs and adversarial establishment/retention controls. Keep historical tests and documents as evidence; do not convert them all into the default product gate.

## 18. Proposed minimum vertical slice

**Starting state and inputs.** A small user workspace contains a supported `software.json`, governance Markdown, and a selected `config.routes/v1` Design profile/config. The profile declares the exact source scope, route-form limits, proposition extraction and binding/candidate rules, required evaluator and method version. The user provides an output root; optionally an expected SHA-256 revision from a prior observation. No preexisting World, route IDs or proposition IDs are required as caller inputs. The profile derives and reports them. This is a **proposed** surface; commands below do not exist today.

1. `design construct --profile config-routes --workspace X --output W0 [--expected-revision R0]` composes `produce_routes` and `construct_software_governance`. It reports exact absolute W0 address, consumed revisions, selected/skipped/unsupported inputs, profile/method, propositions, subjects, coverage and validation. `design list --publications ROOT` lets another session discover retained addresses without guessing the latest one. Refuse unsupported input, duplicate IDs, unsupported correspondence, R0 mismatch and publication failure; no final address on failure.
2. `design inspect --world W0` lists subjects and propositions; `design inspect --world W0 --proposition P` shows statement, source excerpt, candidate/question, bindings, binding rule and both endpoint bases; `--subject S` shows producer facts, manifestation and applicable coverage. The implementation may compose `GovernanceView`, Core assertion/warrant reads and retained blobs. The user selects P and S from these outputs.
3. `design judge --world W0 --proposition P --subject S --artifact J0.json` assembles and verifies a case, invokes the config evaluator named by the profile, checks the exact address/method/citations and writes case+artifact. Output distinguishes `APPLIES/DOES_NOT_APPLY/UNKNOWN`, a finding, and `CONFORMS/CONFLICTS/UNKNOWN` only when APPLIES. Show assertion IDs, evidence and rule for each conclusion. An unbound, ambiguously selected status route remains applicability UNKNOWN, not a software conflict.
4. If UNKNOWN asks for a fact already in W0, `design investigate --judgment J0.json` may expand the case and re-judge on W0. If the required information exists only in retained manifestation/source text, return a proposal with its basis and the input/rule that a new construction would need. If no basis exists, return UNRESOLVED. Do not silently admit a proposal or change J0. The default full case may make the first branch rare.
5. The user corrects `governance.md`, source JSON, or the declared profile rule. `design construct ... --output W1` repeats construction from those exact revised inputs. W0 remains byte-identical/readable; no binding carries forward merely because a route ID matches.
6. `design compare --before W0 --after W1` reports exact addresses; proposition text/evidence and binding/candidate/question/coverage changes by explicit proposition ID; each World's subject snapshots and route facts separately. Same `record_id` is shown as observed correspondence only. If desired, run a **new** Judgment on W1 and place J0 and J1 side by side with their own cases/methods. No generic dependency graph is needed: J0's cited assertion IDs identify its direct basis.

**Success criteria:** a fresh reader with W0/J0 files but no builder session can reproduce each cited observation, see why a binding was emitted and what was unresolved, and distinguish W0 from W1 and J0 from J1; failure states are explicit and leave no claimed fresh publication. **Current reality:** only the fixed-profile build command and manually composed Python calls exist; the `design` examples specify work to build, not available commands.

## 19. What that slice explicitly does not need

No generic Action, workflow/run object, Admission subsystem, Decision/Adoption system, authorization framework, correspondence framework, reconsideration subsystem, proposal queue, maintenance engine, OA Application Runtime, EvidenceInput framework, agent harness, economic benchmark, or frontend redesign is required. ## 21. Independent second opinion

The four-capability account is **sufficient but slightly inflated**. Investigation is a meaningful capability when an UNKNOWN prompts a search, yet the minimum honest product can expose it as an Inspect/Judge continuation rather than a separately maintained subsystem. The missing operation is **publication with declared interpretation and conservative comparison**, not a fifth semantic stage called Revision. The repository has overbuilt research around action/write/reconsideration/platform taxonomies relative to the unfinished user path. It has underbuilt profile-owned semantic establishment, input coverage, exact artifact linkage, and a small user-facing facade. Core does not show a missing fundamental responsibility; the failing cases are Design profile and product composition defects.

## 22. Exact recommended next production work

One implementation agent should deliver the **config-route Design slice**: (1) make the profile accept an explicit workspace/source pair and publish a declared versioned rule for proposition extraction, binding/candidate selection and evaluator choice; (2) retain source **and software** basis for each binding, reject duplicate/unsupported route records, and report consumed revisions/coverage; (3) seal before exclusive fresh-address publication and enforce a supplied expected revision at the producer's acquisition point; (4) add a thin installed CLI/Python facade with JSON `construct`, `list/inspect`, `judge`, bounded `investigate`, and conservative `compare`; (5) bind case+artifact to the exact W address and check citations/results before returning a judgment; (6) verify a W0→correction→W1 path using non-fixture workspace paths, with old bundle/evidence unchanged and UNKNOWN preserved when the rule cannot select an endpoint. Keep changes in Design/profile code and targeted acceptance tests; present a concrete failing Core requirement before touching Core.

If this is too large for one patch, implement the **profile input/rule and safe construct path first**, then the read/judge facade; otherwise a command would merely automate the fixture's hidden assumptions.

## 23. What architecture/research work should stop

Stop designing a generic application platform, action/admission/workflow taxonomy, universal correspondence identity, maintenance engine, or proposal promotion pipeline before the bounded product path works. Stop treating test-local operational loop, route-key persistence, or claimed `COMPLETE` coverage as production guarantees. Stop using package boundaries as product capability proof. Preserve those experiments as falsification evidence and revisit only on a required read that the small slice cannot answer.

## 24. Falsifiers

This recommendation is wrong if a bounded config workspace with declared rules still cannot represent a necessary specification commitment using current relations/grounding; if a real judgment needs a durable semantic fact that cannot be reconstructed from a sealed World, retained evidence or exact artifact; if direct case assertion IDs cannot explain a changed conclusion without a generic dependency graph; if a profile rule cannot distinguish a justified binding from a candidate without an application-wide admission authority; or if users must act on a cross-snapshot “same subject” claim that cannot safely remain observational. A representative non-fixture workspace that passes mechanical validation but systematically emits wrong correspondences would falsify the proposed establishment rule, not Core. Demonstrate those with a failing product read before adding machinery.
